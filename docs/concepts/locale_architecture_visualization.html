Orest Edit / Locale Architecture

One repo, centralized locales, runtime language switch.

The app keeps one shared editor core and moves language-specific behavior into centralized catalogs. The language selector in Settings changes UI labels, prompt suites, LanguageTool language, export metadata, and locale-scoped browser state without cloning the product or forking the editing logic.

Main user outcome The editor can switch between Ukrainian and English inside the same app and get matching UI, prompts, spellcheck, and export behavior.
Main safety rule Locale is runtime state, but drafts, prompt templates, dictionary data, and stale AI results stay locale-scoped so workflows do not overwrite each other.
Main cleanup rule Provider failures must fail loud. Locale work is a good moment to remove synthetic AI fallback responses that look successful.

Switch Flow

What happens when the user changes language

This is the runtime sequence the product should make explicit and safe.

1. User selects a new language in Settings. The app writes `orest-active-locale-v1` and opens a confirmation if the current session already contains locale-bound prompts, spellcheck, or review outputs.
2. Locale catalogs rehydrate the UI. Settings, login, top bar, workflow rail, composer, status copy, compare/history labels, and export labels redraw from the selected locale catalog.
3. Locale-scoped settings and prompts reload. The app reads the selected locale's prompt templates and model-facing labels without overwriting the other locale's custom values.
4. Locale-bound analysis state is invalidated. Spellcheck results, review results, and any analysis generated under the old locale are cleared or marked stale so the UI does not mix languages silently.
5. New requests carry locale explicitly. `patch`, `review`, `proposal`, `image`, and `spellcheck` calls send `locale`, and the server resolves prompts and LanguageTool behavior from that value.
Open Questions

Decisions that still need a product answer

These are the real ambiguities worth agreeing on before implementation starts.

What should happen to the visible manuscript on language switch? Safest v1: keep the current document, switch UI/tooling language, and clear review/spellcheck state. Alternative: switch to the selected locale's saved draft if it exists.
Do custom prompt templates belong to each locale separately? The plan assumes yes. Otherwise one English customization could quietly break the Ukrainian workflow and vice versa.
Should English be only `en-US` in v1, or should we expose `en-GB` later? The architecture can support both, but the first UI can stay simple and default to `en-US`.
Should deployment config still matter after the user switches language? Recommended answer: only as the initial default for fresh sessions. Runtime locale should win after the first explicit user choice.
